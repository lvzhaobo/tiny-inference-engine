# 18-推理引擎对比与进阶路线

本文档回答两个问题：
1. 自研的 engine_minimal（教学版推理引擎）与生产引擎 vLLM、SGLang 差在哪；
2. engine_minimal 继续进阶，1 档、2 档、N 档分别长什么样。

对比的判据先说清：**972 模型（45 词表、6 维、3 头、3 层、972 个参数，纯 attention + 残差，
无 FFN/LayerNorm）在 CPU 上前向只有毫秒级，任何真实性能对比都无意义。** 所以本文对比的是
"调度与内存管理概念的复现度"——即 vLLM/SGLang 的核心机制，engine_minimal 实现了哪些、
还差哪些。这是教学口径，不是性能口径。

---

## 一、当前引擎：engine_minimal 是什么

目录 `tiny-inference-engine`（第 2 个仓库，规划中），四个 Python 文件分层对应真实引擎的四个角色：

| 文件 | 角色 | 内容 |
|---|---|---|
| model.py | 执行器 | 972 权重加载 + 批量前向（变长 mask prefill、KV 增量 decode） |
| engine.py | 调度器 | 请求队列、状态机（QUEUED→RUNNING→FINISHED）、连续批处理、虚拟时钟、TTFT/TPOT/吞吐统计 |
| server.py | 服务层 | 标准库 HTTP：POST /generate、GET /result、GET /metrics |
| demo_multi_user.py | 演示 | 正确性验证（批量前向与单序列前向逐位比对）+ 8 用户时间线 + 串行 vs 连续批处理对比 |

**已实现的概念**：
- 连续批处理：每迭代所有活跃请求各前进一步（产出 1 token），完成的让位、新请求随时插入
- PD 分离（逻辑分离）：prefill 与 decode 是两个独立函数，日志分别标 [P]/[D]
- KV cache：每请求独立缓存，新词元 k/v 先写入、q 再查询含自己在内的全部缓存（自注意力不能丢）
- 调度指标：TTFT（首 token 延迟）、TPOT（每 token 间隔）、排队时长、吞吐
- 虚拟时钟：972 真实耗时看不出调度差异，用虚拟毫秒模拟 GPU 工作量（prefill 每 token 2ms、decode 每步 5ms，常量可调）

**实测数字**（demo_multi_user.py，同一批 8 个请求）：连续批处理比串行（静态 batch=1）快 2.35x，
平均 TTFT 从 74.2ms 降到 7.8ms——"为什么生产引擎不用静态 batch"的量化答案。

**未实现**（也是进阶档位的来源）：页式 KV 管理、采样参数、抢占、投机解码、PD 分离双实例、
任何 GPU 相关优化（kernel/并行/量化）。

## 二、与 vLLM、SGLang 的对比

### 2.1 三个引擎一句话定位

| 引擎 | 定位 |
|---|---|
| engine_minimal | 教学引擎：用最小模型 + 纯 Python 复现调度概念，每个状态切换可打印 |
| vLLM | 生产引擎（UC Berkeley，2023）：PagedAttention + 连续批处理，高并发下显存效率与吞吐优先 |
| SGLang | 生产引擎（斯坦福系，2024）：RadixAttention 前缀共享 + 结构化生成，多轮对话/Agent 场景优先 |

### 2.2 维度对比表

| 维度 | engine_minimal | vLLM | SGLang |
|---|---|---|---|
| 定位 | 教学复现 | 高性能通用服务 | 高性能 + 新特性探索 |
| 核心创新 | 无（复现概念） | PagedAttention（分页 KV） | RadixAttention（前缀共享树） |
| 批处理 | 连续批处理 ✓ | 连续批处理 + 抢占 | 连续批处理 + 前缀感知调度 |
| KV 管理 | 每请求连续缓存，完成整体释放 | 分页块池，块级分配/回收 | 分页块池 + 前缀 radix tree，相同前缀跨请求复用 |
| 调度策略 | FCFS（先到先服务） | FCFS + 抢占（preemption）+ 优先级 | FCFS + 前缀命中优先（cache-aware scheduling） |
| 并行 | 单线程 CPU | TP/PP/DP 多卡，CUDA graph 捕获 decode 循环 | 同 vLLM，另有 FlashInfer 内核 |
| 内存优化 | 无 | AWQ/GPTQ/FP8 量化、专属 kernel | 同左 + Radix 前缀去重 |
| 采样 | 贪心（argmax） | 温度/top-k/top-p + 投机解码 | 同左 + 结构化输出（约束解码） |
| PD 分离 | 逻辑分离（两个函数） | 支持 prefill/decode 分实例部署（disaggregated serving） | 同 vLLM |
| 接口 | 极简 HTTP 三接口 | OpenAI 兼容 API + 流式 | OpenAI 兼容 API + SGLang DSL 前端 |

### 2.3 两个生产引擎的核心机制（engine_minimal 缺的部分）

**vLLM 的 PagedAttention**：把每请求的 KV 切成固定大小块（如 16 token/块），放入全局块池，
请求按需申请、完成即归还。价值：① 消灭"每请求预留最大长度"造成的显存浪费（KV 显存公式见 6 号文，
浪费可达数倍）；② 块可离散存放，不要求连续显存。对应到 engine_minimal：现在每请求独立连续缓存，
理论上也按需增长、无预留浪费，但**没有块池和碎片管理**——块池的分配/回收/碎片统计就是进阶 2 档。

**vLLM 的连续批处理 + 抢占**：迭代粒度调度（engine_minimal 已复现）。vLLM 多了抢占：新请求
到来但显存不够时，把某个长请求的 KV 换出（swap）或丢弃重算（recompute），腾出空间。对应
engine_minimal 的 max_batch 上限是"硬上限"，无抢占机制。

**SGLang 的 RadixAttention**：KV cache 按前缀组织成 radix tree（字典树）。多个请求共享相同
前缀（如共用同一个 system prompt、多轮对话共享历史）时，前缀部分 KV 只算一次、全部命中复用。
对应到 engine_minimal：每个请求 prefill 都从零算，即使 prompt 相同也不复用。

**共有的 GPU 侧优化**（engine_minimal 在 CPU 上无法复现、也不该复现）：
- CUDA graph：把 decode 的整条 kernel 序列录制为图，消除每步的 CPU-GPU 启动开销
- FlashAttention：分块在线 softmax，避免把 S×S 注意力矩阵落到 HBM（见 15 号文）
- 量化 kernel：AWQ/FP8 的专用矩阵乘，减少显存与带宽占用（见 11 号文）

### 2.4 对比结论

engine_minimal 与生产引擎的差距分两类：
1. **调度概念类**（页式 KV、抢占、前缀共享、投机解码）——可以在 972 上继续复现，就是本文第三节的进阶档位；
2. **算力/硬件类**（CUDA graph、FlashAttention、多卡并行、量化 kernel）——必须在 GPU 上做，本机不做，
   对应关系与原理分别见 10、15、16、11 号文。

## 三、进阶路线：1 档 → 2 档 → N 档

档位判据：每档是"向生产引擎靠近一步"的一个功能块，全部可在本机 972 模型上运行并打印中间量，
每一档完成后 demo 都能讲一个对应的生产引擎机制。

### 进阶 1 档：服务完整性（采样 + 流式 + OpenAI 兼容接口）　约 1 天

现在引擎只有贪心采样、一次性返回、三个自定义 HTTP 接口。补三件事：
- **采样参数**：temperature（logits ÷ T 再 softmax）、top-k（只保留前 k 个候选）、top-p（累积概率截断）。
  教学点：temperature 如何把 logits 分布"抹平/锐化"（12 号文指标的生成质量侧）
- **流式输出**：HTTP 侧用 SSE（Server-Sent Events）或逐行 chunked 返回，每生成一个 token 推一条。
  教学点：为什么用户感知延迟约等于 TTFT 而非总耗时
- **OpenAI 兼容接口**：/v1/chat/completions 的 messages 字段格式映射到 prompt。教学点：生产引擎的统一接入层
  抽象（14 号文）

### 进阶 2 档：页式 KV（PagedAttention 复现）　约 1~2 天

对应 10 号文的核心。改动点：
- KV 池：固定块大小 PAGE_SIZE（如 8 token/块），全局块池，每请求持有"块指针列表"
- prefill/decode 时按需申请块，写满一块再申请下一块；完成时整条链归还池
- 指标：池中块总数、已用块、碎片率（每个请求最后一块的平均空位比例）
教学点：同样的请求流，页式 vs 连续两种 KV 管理的块利用率对比——这就是 PagedAttention 论文
要解决的"显存浪费"问题的可动手验证版。

### 进阶 3 档：抢占与调度策略　约 1 天

- **抢占**：新请求 prefill 需要块但池已满 → 选一个策略（换出最新请求 / 换出最长请求）腾块，
  被抢占请求从断点重算（recompute）
- **优先级队列**：waiting 队列从 deque 换成按优先级排序的结构
- **调度策略对比实验**：FCFS vs 短作业优先 vs 抢占，同一批请求跑出三份 TTFT/吞吐对比表
教学点：vLLM 的抢占策略（swap vs recompute 的取舍）与调度公平性。

### 进阶 4 档：投机解码（自造 draft 模型）　约 1~2 天

投机解码（speculative decoding）在生产引擎里是"小 draft 模型快速生成 k 个候选，大模型一次
验证"（vLLM/SGLang 都支持）。972 模型没有独立小模型，但有现成的替代：**用 3 层模型的前 1 层
截断当 draft、全 3 层当验证模型**——同一个权重文件拆出天然的小/大模型对。
- draft 用 1 层 + KV 增量快速自回归 k 步，产出 k 个候选
- 验证模型把 k 个候选一次性走 3 层（一次 decode 步验证 k 个），逐个比对贪心结果，接受一致前缀
教学点：接受率与加速比的关系（draft 越准、接受前缀越长、加速越接近 k 倍）；为什么解码是
访存密集而非算力密集（5 号文）。

### 进阶 5 档：PD 分离双实例 + KV 传输模拟　约 1 天

对应 7 号文 PD 分离架构的落地产物。改动点：
- 两个 Engine 实例：prefill 实例只做 prefill，decode 实例只做 decode
- KV 传输模拟：prefill 完成后把 KV"传输"给 decode 实例（实际是同进程内引用传递，但日志与
  虚拟时钟按网络传输计费，如每 token 0.1ms）
- 对比实验：合并部署 vs 分离部署的虚拟总耗时、prefill 突发对 decode TPOT 的影响
教学点：PD 分离的动机——prefill 算力密集、decode 访存密集，混在一起会互相拖慢；
分离后 TTFT 与 TPOT 各自稳定（7 号文 GPU 配置图的数值支撑）。

### 进阶 N 档：真实边界（本机不做的部分）

以下各档必须 GPU/多卡/真实模型，属于"教学讲解 + 云实例演示"范畴，不在 engine_minimal 上复现：
- **CUDA kernel 层**：FlashAttention 等价实现、CUDA graph 录制 decode 循环（15 号文）
- **多卡并行**：TP/PP/DP 的切分与通信（16 号文）
- **量化**：AWQ/FP8 权重与 kernel（11 号文，本机已有 972 量化对比实验作概念铺垫）
- **真实模型接入**：972 → GPT-2（124M）→ Qwen3 系列，用 transformers/vLLM 真引擎跑对照实验，
  与 engine_minimal 的虚拟时钟数字互相印证（主干 10 档位规划）

### 3.1 汇总表

| 档位 | 内容 | 工作量 | 对应生产引擎机制 | 对应文档 |
|---|---|---|---|---|
| 1 | 采样参数 + 流式 + OpenAI 兼容接口 | ~1 天 | 统一接入层 | 12、14 号 |
| 2 | 页式 KV（块池/碎片率） | 1~2 天 | vLLM PagedAttention | 10 号 |
| 3 | 抢占 + 优先级 + 策略对比 | ~1 天 | vLLM 抢占调度 | 7、10 号 |
| 4 | 投机解码（1 层 draft + 3 层验证） | 1~2 天 | speculative decoding | 5 号 |
| 5 | PD 分离双实例 + KV 传输模拟 | ~1 天 | disaggregated serving | 7 号 |
| N | CUDA kernel / 多卡并行 / 量化 / 真实模型 | GPU 云实例 | 生产引擎完整形态 | 11、15、16 号 |

### 3.2 建议顺序

按"依赖关系 + 教学价值"排序：**2 档（页式 KV）→ 1 档（服务完整性）→ 5 档（PD 分离）→ 3 档
（抢占）→ 4 档（投机解码）**。理由：
- 2 档是 3 档的前置（抢占腾的是块池），也是 10 号文最需要落地验证的部分，教学价值最高；
- 1 档独立性强，可与 2 档并行；
- 5 档只用现有两个函数拆实例，改动最小；
- 3 档依赖 2 档的块池，4 档独立但工作量最大，放最后。
